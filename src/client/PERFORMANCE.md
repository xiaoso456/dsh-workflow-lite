# 前端性能：设计与验收

画布、实例视图在大图（几百张卡）下还能跟手，靠的是下面几样自己做的东西。这份文档写它们**为什么这么做、边界在哪、怎么验**；
改到相关代码前先读一遍，改完按「验收」一节量一次。

## 开销从哪来

宿主页面有一条带 `:has()` 的样式规则。它的后果是：**视图里插入或摘掉任何一个元素，整页样式都要重算**，重算的开销和页面上的元素数成正比
（400 张卡全挂着时一次约 400ms）。只改属性、改文字不会触发整页重算。

所以前端的性能问题几乎都归结为两件事：

1. **页面上的元素太多**：每次重算都贵。→ 只挂视口附近的卡片和线（[只挂视口附近的](#只挂视口附近的)）。
2. **热路径上插拔元素**：打字、拖动、平移、轮询时每帧都在插拔。→ 只改属性 / 文字，算出来一样的就沿用（[打字](#打字不卡)、[比较与共享](#比较与结构共享)）。

另外两条机制上的事实：

- `element.animate()` 会当场把同一次提交里挂起的样式改动一起算掉（强制同步样式重算），热路径上别调。
- React 18 的受控 `<textarea value>` 每次渲染都重写里面的文字子节点（一次插拔）。

## 总览

| 问题 | 做法 | 代码 |
|---|---|---|
| 元素太多 | 只挂视口附近一块区域里的卡片和线，区域有滞后 | `model/cull.ts`、`ui/canvas/hooks/useCulling.ts` |
| 没挂的卡片也要参与看全图、整理排版 | 卡片尺寸表跟着画布走，看全图按文档坐标算 | `model/canvasGeometry.ts`、`ui/canvas/hooks/useCanvasGeometry.ts` |
| 展示卡摘下再挂回来要重读、闪「读取中」 | 读取结果按「目标 + 信号」缓存，看过的展示区直接挂内容 | `app/readCache.ts`、`ui/display/ResourceDisplay.tsx` |
| 打字时整张图重算 | 结构、走线没变就沿用；检查结果晚一拍、保存前当场再查；草稿停手再存 | `model/docShape.ts`、`app/useStable.ts`、`app/useRunGraph.ts` |
| 打字时 textarea 每个字插拔一次 | 只改 `value` | `ui/kit/TextArea.tsx` |
| 换字动效强制样式重算 | 换属性重放 CSS 动画 | `ui/motion/swapText.tsx` |
| 每帧序列化比较、轮询换掉整份对象 | 逐项比较、结构共享、草稿写时复制 | `model/samePlain.ts`、`model/runDraft.ts` |

## 只挂视口附近的

`model/cull.ts`（纯函数）+ `ui/canvas/hooks/useCulling.ts`（接到画布上）。卡片数达到 `CULL_MIN_NODES`（50）才启用，小图全挂，行为和以前一样。

### 区域与滞后

React Flow 自带的 `onlyRenderVisibleElements` 每次视口变化都按视口重挑，平移中边缘的卡片不停地插拔——在 `:has` 规则下，每一次都是整页重算。
这里换成**比视口大一圈、而且有滞后的区域**：

- **区域** = 视口每边再多出 `MARGIN`（0.75）倍视口宽 / 高。区域里的卡片和线全挂着。
- **换区域的时机**（`decide`）：
  - `keep`：视口还在区域里，离区域边还有 `RESERVE`（0.25 倍视口）以上的余量 —— 什么都不做。**平移中绝大部分时间都是这一种，零插拔。**
  - `now`：余量不够了（快看到没挂的地方）—— 当场换。快速平移时偶尔发生，插拔的只是新进、离开的那一条。
  - `later`：缩放变了 `ZOOM_DRIFT`（1.4 倍）以上，或视口中心偏离区域中心超过 0.375 倍视口 —— 等视口停下来（`whenStill`）再换，插拔落在停下的那一刻。
- 视口每动一下，`useCullRegion` 只做几次加减比较，不重渲染画布；要换区域时才更新一次状态。

### 区域里挂哪些（`mountedIn`）

- 外框（四周多算 `CARD_PAD`）碰到区域的卡片。尺寸用量出来的，没量过用标称（`canvasGeometry.ts` 的 `cardRect`）。
- 外框碰到区域的线：外框 = 两张卡的外框 + 走廊（`lane`）+ 绕行折点（`bend`），四周多算 `LINE_PAD`。
- **挂着的线两头的卡片都挂上**（React Flow 画一条线要两头的卡都在）。横穿视口的长线两头都在区域外，也照样画。
- **钉住**：选中的卡片 / 线、正在拖的卡片、正在拉线的那张卡，不管在哪都挂着。所以「定位」到视口外的一步、拖着卡片自动平移都不会掉。
- 挑出来的和上次一样（`sameMounted`），就沿用上一次交给 React Flow 的数组。

### 不变式（改代码时别破坏）

- 交给 React Flow 的是**过滤后的数组**，其余一切（撤销、删除动效 `useCanvasExits`、检查结果、走线）都按**整份**文档算。删除动效比的是整份 id，挂没挂不算删掉。
- 重挑只看 `routeDoc`（结构、位置、尺寸变了才换的那份文档）、区域、钉住的 id、尺寸表版本；**拖动中每帧变的坐标不进依赖**。
- 新加「不管在不在视口都要在」的东西（比如某种浮层要贴着一张卡），加进 `useCulledFlow` 的钉住列表。
- 任何「按 React Flow 里的节点算」的逻辑（`getNodes`、`getInternalNode`、`fitView`）在大图上只看得到挂着的那部分，要改成按文档 + 尺寸表算（见下一节）。

## 画布几何

`model/canvasGeometry.ts`（卡片矩形、整图外框）+ `ui/canvas/hooks/useCanvasGeometry.ts`。

- **尺寸表**：React Flow 量出来的卡片尺寸记在一张按画布（`ReactFlowProvider` 的 store）区分的表里，卡片摘下后也留着；挂回来时带回给 React Flow，不用重新量、走线也不跳。
  - 按 store 的 `getState` 认表，不按 `useStoreApi()` 的返回值：后者每处调用各包一层新对象，按它认的话画布、整理排版、看全图各拿一张表，画布外面读到的是空表、全按标称尺寸算。`tests/client/cardSizes.spec.ts` 钉着。
  - 画布换了文档（`loadKey` 变了）先清空：模板和实例共用一个画布，不同工作流的卡片 id 也会重名，别的文档量的尺寸不能拿来排版、看全图。
- **看全图**：`fitDoc` 按文档里的坐标和尺寸表求外框，用 `getViewportForBounds` 算视口，不调 `fitView`（它只认挂着的节点）。留空统一走 `fitPadding`、自动看全图的缩放范围是 `AUTO_FIT`。
- **整理排版**：`sizeOf` 从尺寸表取，不问 `getInternalNode`。

## 挂回来不闪

展示卡平移出去被摘下、再挪回来时，组件里的状态都没了。`app/readCache.ts` 是一个按「目标 + 信号」记的小 LRU（条数、大小两个上限）：

| 读取 | 目标 | 信号 |
|---|---|---|
| `useRunFile`（整份读） | 实例 + 读取目标 | 调用方给的版本（展示卡给修改时间）；存下的旧版用常量；**不给版本的调用方不缓存** |
| `useRunLines`（按行读） | 实例 + 目标 + 读法 + 筛选 | 修改时间 |
| `useDisplayImage` | 实例 + 资源#项 + 第几版 | 修改时间 / 常量 |
| `useRunHistory` | 实例 + 资源#项 | 变化次数 |
| `useRunImages`（文档里的图） | 实例 + 文档 + 图的路径 | 文档的修改时间 |
| 图片墙的列表 / 每格 | 实例 + 资源#项（/ 文件名） | 文件夹 / 那张图的修改时间 |

挂上时用 `useState` 的初始化函数先查缓存：命中就第一帧直接是内容，不发请求。信号变了（文件改了）照常重读。
「刚更新」的提示只在同一次挂载里读到新版本时亮，挂回来不会误亮。

`ResourceDisplay` 的 `useSeen` 另记**看过的展示区**：本来要等进视野、画布停下才挂内容，看过的挂上就挂。

## 打字不卡

- **结构 / 走线没变就沿用**（`model/docShape.ts` + `app/useStable.ts`）：改提示词、标题时文档每个字都换一份，但 `sameStructure`（节点 id、种类、连线对象）没变就沿用图分析和步骤事实，`sameRouting`（再加位置、估算尺寸、走法相关的连线字段）没变就沿用全图走线。判断必须**精确**：判成一样的，算出来一定一样（`tests/client/docShape.spec.ts` 对着算）。给这些计算加了新的输入，要同步补进判断。
- **画布晚一拍**：只改文字时画布用 `useDeferredValue` 的那份，按键那一帧不等画布。
- **实例图的检查晚一拍、保存前当场再查**：`useRunGraph` 的检查结果按晚一拍的那份图算；`problemsNow()` 按眼前的图同步再查一遍，保存前拦住。
- **草稿停手再存**：实例图的草稿序列化后写浏览器存储，停手 400ms 再写；换实例、关页面时当场写掉。
- **`TextArea`**：只改 `value`，不让 React 重写文字子节点（受控 textarea 的坑见上）。多行输入一律用它。
- **`SwapText`**：换字不重挂元素，切换 `data-fresh="a" / "b"` 重放同样的关键帧。

## 比较与结构共享

`model/samePlain.ts`：

- `samePlain(a, b, skip)`：逐项比内容，第一处不同就停，口径同 JSON（值为 `undefined` 的键等于没有）。画布每帧判断卡片、连线对象变没变用它，替代两边各 `JSON.stringify` 再比字符串；回调放进 `skip`。
- `shareSame(prev, next)`：结构共享。实例轮询读回来的整份数据里，和上一份相同的部分（任何一层）换回上一份的对象，整份相同就交回上一份——按对象身份记的 `useMemo` 只在真变了的那一支上重算。

`model/runDraft.ts` 的 `applyDraft` 只复制改到的步骤，其余步骤原样沿用。

### 真浏览器功能验收：`tests/cdp-big.mjs`

自备一次性实例，400 张卡：小图照旧全挂；大图只挂一部分、挂着的线两头都在；看全图按整张图算；小幅平移零插拔；平移很远换挂一块；检查结果里定位视口外的一步；拖卡片写进图；两头都在视口外的长线照画；实例里的展示卡平移出去被摘下、挪回来那一刻内容就在。

```bash
node tests/lib/cdp-chrome-launch.mjs 9222   # 另开一个窗口
pnpm run build
node --experimental-strip-types tests/cdp-big.mjs
```

最后一项做过反证：关掉读取缓存和「看过的」记忆，它报「展示卡挂回来时不是直接显示内容：["loading"]」。

### 性能场景：`tests/perf/canvas-scenarios.mjs`

```bash
node --experimental-strip-types tests/perf/canvas-scenarios.mjs --copies 16 --out a.json   # 400 张卡
node --experimental-strip-types tests/perf/canvas-scenarios.mjs --copies 4 --out b.json    # 100 张卡
```

平移、缩小后平移两项另记「插拔」（视图里插入 + 摘掉的元素数），应为 0。机器噪声大：**各跑两遍取平均，只比整套跑的结果**（`--only` 单跑一项的数和整套里的不可比）。

### 结果（headless Chrome，各两遍平均）

400 张卡，同一个新起的 Chrome 里三组交替着量：「起点」= 这一轮性能工作之前的代码，「不裁剪」= 现在的代码把门槛设成无穷大，「现在」= 现在的代码。
headless Chrome 没开 GPU，绝对数比真机大，看相对变化。

| 场景 | 指标 | 起点 | 不裁剪 | 现在 |
|---|---|---|---|---|
| 切到大图 | 停稳 | 9789ms | 6489ms | 2065ms |
| 切到大图 | 长任务 | 15842ms | 11218ms | 2361ms |
| 打开切换列表 | 停稳 | 2770ms | 1522ms | 810ms |
| 拖步骤 | 长任务 | 16739ms | 11379ms | 632ms |
| 拖步骤 | >33ms 帧 | 115 | 121 | 50 |
| 平移画布 | 长任务 | 17812ms | 14265ms | 253ms |
| 平移画布 | >33ms 帧 | 123 | 123 | 6 |
| 缩小后平移 | 长任务 | 15167ms | 13893ms | 202ms |
| 平移两项 | 插拔 | 0～1 | 0 | 0 |
| 模板里改提示词 | 按键 p50 | 1376ms | 220ms | 64ms |
| 实例里改提示词 | 按键 p50 | 1312ms | 208ms | 56ms |
| 实例静置 16 秒 | 长任务 | 2496ms | 2407ms | 0ms |

「起点 → 不裁剪」主要是打字那几样（`TextArea`、`SwapText`、精确沿用、晚一拍的检查）；「不裁剪 → 现在」是只挂视口附近的。

和 React Flow 自带的 `onlyRenderVisibleElements` 比（另一个 Chrome 里、较早的代码上量的，只有平移、切图两项可比）：平移长任务 2034ms → 91ms、>33ms 帧 22 → 2；切到大图停稳 2219ms → 824ms。

更小的图（同一个 Chrome 里门槛设成 0 和无穷大前后接着量）：

| 卡片数 | 切到大图停稳 | 拖步骤 >33ms 帧 | 平移长任务 | 模板里打字按键 p50 |
|---|---|---|---|---|
| 100 | 1303 → 708ms | 6 → 7 | 82 → 56ms | 40 → 24ms |
| 50 | 1790 → 770ms | 35 → 3 | 172 → 0ms | 68 → 32ms |

50 张卡时一屏通常已经装不下，裁剪照样省；一屏装得下的小图没有可省的，门槛据此定为 50。

纯计算（`tests/perf/bench-model.ts`，Node 里）：400 张卡时换区域挑一次要挂的 0.14ms，打字时判一次「走线没变」0.01ms 以内。

### 试过、没要的

- **缩小时简化卡片（LOD）**、**展示区 `content-visibility: auto`**：在上面那个 Chrome 里和「现在」交替各量两遍（用 `--css` 注入：LOD 用隐藏卡片里的文字、图标近似）。缩小后平移主线程 −11% / −10%，但长任务 +9% / +11%、>33ms 帧都是 4 → 3，其余场景在 ±10% 噪声内。裁剪之后屏幕外的卡片和展示区已经摘掉了，这两样没有可省的，不做；以后卡片明显变重时再量。
- **背景点阵换成 CSS 背景**：平移时没有可见差别。
