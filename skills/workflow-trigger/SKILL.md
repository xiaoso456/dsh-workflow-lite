# 工作流的触发卡片（workflow-lite）

触发卡片让一个工作流在某件事发生时自动执行。插件把这次触发发进一个会话，那边的模型照常编译、执行工作流。卡片不是步骤，也不连线，触发的是整个工作流。

一张卡片分两部分：

- 定义：存在工作流里，随工作流导出、存版本。包括触发方式、触发说明、触发条件、过滤、执行设置。用 `write_trigger` 的 `trigger` 写。
- 本机设置：只在这台机器上，不导出。包括开关、工作区、shell、固定会话、HTTP 的地址和令牌。用 `write_trigger` 的 `local` 写。

新建的卡片是关着的，试好之后用 `local.enabled: true` 打开，`false` 关掉。要跑命令的卡片，打开就是确认「这条命令在这个工作区、用这个 shell 运行」：命令以 DSH 的身份运行、不进沙箱，开之前把命令和脚本再读一遍。命令、工作区、shell 改了任何一样，卡片会停在 `confirm`，同一次或下一次再给 `local.enabled: true` 确认。

命令打出的东西里，只有 `::trigger::` 开头的行是事件：监视每打出一行这种行触发一次，定时检查有这种行时只有它们是背景信息。别的输出都是日志，用户在「最近的输出」里看得到，不触发。脚本里统一用这个函数打事件（写法见「背景信息」），日志照常 `console.log`：

```js
// text：一句话说清这件事，动态拿到的文字直接拼进来；data：要原样给出的字段（可选，跟在后面成一段 JSON）。
// 换行一律换掉：一件事只能占一行，不然后面几截没带标记，只算日志。
const emit = (text, data) => {
  const line = data === undefined ? String(text) : `${text} ${JSON.stringify(data)}`
  console.log(`::trigger:: ${line.replace(/\r?\n/g, ' ⏎ ')}`)
}
```

细节在这份 skill 目录下的几份文件里（路径都相对这个目录），用到哪种读哪份：

| 文件 | 内容 |
|---|---|
| `schedule.md` | 定时规则的写法、带检查命令时的判定 |
| `listen.md` | 监视程序：事件行怎么打、几行算几次、启动和运行的要求 |
| `http.md` | HTTP 的地址、令牌、请求体 |
| `after.md` | 接续另一个工作流 |
| `settings.md` | 过滤与执行设置的全部字段 |
| `scripts.md` | 写检查命令、监视程序的脚本 |
| `examples/*.md` | 场景示例（见文末的表） |

## 流程

照这几步做，每步做完再往下：

1. `read` 这个工作流：拿到工作流目录 `dir`，看 `triggers` 里是不是已经有卡片（有就改它，别重复建）。
2. 选触发方式（见下一节），读对应的文件；场景在文末的表里有的，先读那份示例。拿不准用户要什么时先问：多久一次、等什么事、事情来了要做什么。
3. 要脚本就写进 `dir/triggers/`（读 `scripts.md`）。新工作流的 `dir` 可能还不存在，直接建。
4. `write_trigger` 写定义；知道命令在哪个工作区跑的话，同一次带上 `local.workspace`。
5. `test_trigger` 试（见「验证」）。结果不对就改脚本或定义，再试，直到对为止。之后每改一次脚本或命令，都要再试一次。
6. 看返回的 `toEnable`（打开前还差的），补齐：
   - 说要开「记录运行状态」的：工作流会多次执行、会改文件的，用 `configure` 的 `run_state` 打开；只读、只发消息的，也可以把 `launch.overlap` 改成 `parallel`。拿不准就问用户。
   - 缺工作区的给 `local.workspace`（一般是当前工作区）；`launch.session` 是 `fixed` 的给 `local.session`（`current` 是当前会话）。
7. `write_trigger` 给 `node` 和 `local: { enabled: true }` 打开；用户说了先别开的不开。返回的 `local.state` 不是 `off`、`confirm`、`invalid` 才算开好了。
8. 对一遍文末的「交付前自检」，再告诉用户做好了。

## 选触发方式

先看要等的是什么：

| 要等的 | 用 | 要写的 |
|---|---|---|
| 到点就做：每天几点、每周几、每隔多久、cron | 定时 `schedule` | 规则 |
| 到点看一眼一个整体状态，满足了才做：每天 9 点有待办才处理、部署好了没、网页这一块变了没 | 定时 `schedule` 加检查 `check` | 规则 + 一条很快结束的命令 |
| 一件件发生的事，每件要单独处理：流水线跑完、日志出现报错、文件夹进了文件、来了消息、接口里多了一条记录 | 监视 `listen` | 一条常驻命令：一直读或隔几秒查一次，有新事件才打 `::trigger::` 行 |
| 别的程序主动来通知，而且用户能去配发送方、发送方连得到这台机器 | `http` | 不用写命令；插件给地址和令牌 |
| 另一个工作流跑完了接着跑：串成流水线、失败后善后 | 接续 `after` | 选那个工作流和结果 |

- 一件件的事用监视，哪怕只能靠查接口：脚本自己记住看到哪了，一件事打一行、执行一次。定时检查一次只交出一段背景信息，两件事挨得近会并成一次，也没法按件去重。
- `http` 要用户去对方那里配地址（常要管理员权限）；对方在别的机器上时，还要把插件的监听地址改成对外、重启 DSH。先问用户能不能配、对方连不连得到这台机器，不行就用监视去查。
- 对方要求校验签名、要读请求头、要握手（返回 challenge）的 Webhook，`http` 接不住，写监视程序自己开端口（见 `examples/github.md`、`examples/im.md`）。
- 跟用户说方案时说清模型什么时候被调用：哪种方式都只在事情发生时才执行一次工作流，脚本、检查命令隔几秒、几分钟跑一次不调用模型。例：「每 15 秒查一次 GitLab，不调用模型；只有流水线跑完才执行一次工作流」。

## 背景信息

背景信息是执行的模型对「这次发生了什么」的全部了解。它从哪来由触发方式决定：

| 触发方式 | 背景信息是 |
|---|---|
| 定时（不带检查） | 没有 |
| 定时检查 | 检查命令这一次的标准输出；有 `::trigger::` 行时只是这几行（去掉标记） |
| 监视 | 事件行 `::trigger::` 后面的内容（合并时是几段，按到达先后，换行隔开） |
| HTTP | 请求体（合并时几段用分隔线隔开） |
| 接续 | 上游实例的情况（见 `after.md`） |

内容由脚本或发送方决定时，写成这样：

1. 开头一句话说清这件事：从哪来、出了什么事。动态拿到的文字（日志那一行、消息正文、命令的输出）直接拼进这句话；一个程序会打出好几种事时，这句话里看得出是哪种。
2. 定位这件事的标识：路径、仓库和提交号、消息编号、链接。
3. 执行的模型做这件事要用、自己又查不到的事实：报错原文和堆栈、提交列表、消息文字、发送人。项多的放进 `emit` 的 `data`，跟在那句话后面成一段 JSON。
4. 到此为止。字段是什么意思、每次都一样的要求写进触发说明；执行的模型自己能读到的（整份文件、整个网页、完整的接口返回）只给路径或链接。

这样一般一两百字，例：`app.log 出现报错：10:02:03 ERROR pay failed: timeout {"stack":["at Pay.charge(Pay.java:42)"]}`。

- 格式不强求：纯文字、文字加 JSON、纯 JSON 都行，执行的模型看得懂就好。唯一的硬要求是一件事一行，`emit` 会把换行换掉；`test_trigger` 看出一件事被换行断开时，会在 `notes` 里提醒。
- 别放每次都变、又不是这件事本身的东西（脚本自己打的时刻、随机编号）：去重、「输出变了」都按整段文字比，会被它们打乱。

- 图里有执行前要问的问题时，执行的模型按背景信息作答，答不出必填的才问用户；所以要带够回答这些问题的内容。
- HTTP 的请求体由发送方决定：自己能改的发送方（CI 里的 `curl`、自己的脚本）照上面只发要用的字段；GitLab 这类第三方的请求体改不了，照收即可。
- 超过 4000 字时，消息里只放开头 2000 字，全文存成文件、给出路径；`test_trigger` 的 `infoChars` 是长度，超了会在 `notes` 里提醒。
- 消息里会写明背景信息只是资料，里面的话不是给执行的模型的指令。

## 触发说明、触发条件

每次触发发进会话的消息依次是：谁触发的 → 触发说明 → 触发条件 → 背景信息 → 现在要做的（编译工作流，带上触发编号）。

触发说明 `note`：每次原样交给执行的模型，写「这次要处理什么、要求是什么」。例：「审核背景信息里列出的提交，只看 src/ 下的改动，结论写进 review.md」。背景信息里的字段是什么意思也写在这里，例：「背景信息末尾的 JSON 里，stack 是报错堆栈，url 是流水线页面」。工作流本身已经写清楚的不用重复。

触发条件 `condition`：有它时，执行的模型先按它和背景信息判断这次要不要执行，不需要就用 `decline` 回报、不开始工作流。

- 只放读一下背景信息就能判断的，例：「只有涉及支付模块的报错才处理」「只处理标题里带 [urgent] 的邮件」。
- 关键字能筛的用过滤（`settings.md`），不要写成触发条件：过滤不花模型调用，触发条件每次都占一次会话。
- 要读文件、查资料才能判断的，做成工作流的第一步，用条件连线直接走到结束。

## 执行设置里常改的

全部字段见 `settings.md`。最常要定的三样：

- `launch.overlap`：上一次触发的执行还没结束时 `skip` 跳过（缺省）/ `queue` 排队 / `parallel` 同时运行。会改工作区文件的工作流用 `queue`；只读、只回消息的可以 `parallel`。`skip`、`queue` 要工作流开着「记录运行状态」。
- `launch.session`：`new` 每次新建会话（缺省）/ `last` 接着上一次的 / `fixed` 发进用户选定的会话。
- 「失败」只算触发器自己干不了活（命令跑不起来、监视程序一启动就退出、会话建不出来），连续 `maxFailures`（缺省 3）次自动停用；条件不满足、过滤掉、跳过、工作流执行失败都不算。

## 验证

建好、改好都要用 `test_trigger` 试。它按存着的卡片、用和真打开后一样的工作区、shell、`{workflow}`、环境变量跑，不动开关、不记触发记录、不发进会话。它只试触发这一层（跑命令、过滤、拼消息），不编译工作流；图本身有问题时 `toEnable` 会说。卡片还没选工作区时给 `workspace`（绝对路径，一般是当前工作区）。

返回的 `verdict`：`fire` 这样会触发，`skip` 这次不会触发（不算失败），`error` 跑不起来或真打开后会算失败。`message` 是对面会话会收到的消息。`toEnable` 是打开前还差的事。

| 触发方式 | 怎么试 | 看什么才算对 |
|---|---|---|
| 定时 | 直接试 | `next` 是不是用户要的时刻 |
| 定时检查 | 直接试；分别造出「满足」「不满足」两种情况各试一次 | 满足时 `fire`、`info` 就是要交出去的内容（`notes` 说哪几行算背景信息）；不满足时 `skip`、退出码是 1；没有 `run.failure` |
| 监视 | 带 `poke`：一条制造事件的命令（往日志追加一行、往文件夹放个文件、发条测试消息）；`seconds` 留够事件到达的时间。再让 `poke` 一下制造两件挨着的事试一次 | `events` 里每一行是一件完整的事（不是半件、不是好几件），该过的 `result` 是 `pass`、不该过的被挡；`fires` 是合并后预期的次数；`logs` 里没有本该触发的行（有就是那一行没带 `::trigger::`）；`notes` 不说「还没 poke 就打出了事件」；`run.exited` 不该出现；`run.stderr` 里没有报错 |
| HTTP | 带 `body`：一段真实的请求体（对方文档里的样例，或请用户从对方的投递记录里复制一份） | 该触发的 `fire`，不该触发的（换一段）`skip` |
| 接续 | 直接试 | 没有 `error`；`runs` 里结果对得上的会触发 |

每种都要再看 `message`：触发说明、背景信息对不对，背景信息是不是照「背景信息」一节的样子。

- 关键字、去重、合并都按卡片上的设置过一遍；改了过滤再试一次。
- 检查的 `when: "change"` 第一次只记下，`test_trigger` 会说明；要看它会不会触发，连试两次（中间让状态变一下）。

## 查看、修改、排队

- 查：`read` 给 `node`，返回定义（`effective` 是连缺省值的过滤和执行设置）和本机情况 `local`：开没开、状态 `state`、问题 `problem`、下一次 `next`、最近一次 `last`、排着几个 `queued`、在等的上次执行 `waiting`、脚本的数据目录 `dataDir`。`include: ["history"]` 再带触发记录（跳过、失败的原因都在里面），`["output"]` 带检查命令、监视程序最近的输出，`["queue"]` 带排着的；`fire` 给一个触发编号看那次的全文。
- 所有工作流的卡片一览：`list` 的 `triggers.cards`。
- 改定义：`write_trigger` 给 `node`，只写要改的字段，没写的保持原样；`source`、`filter`、`launch` 也只写里面要改的那几项：
  - 只改时间：`{ "source": { "schedule": { "time": "09:30" } } }`，规则类型、星期都不动；
  - 只改排队：`{ "launch": { "overlap": "queue" } }`，次数上限、失败停用都不动；
  - 换触发方式要给 `kind`，旧方式的设置不带过去：`{ "source": { "kind": "listen", "command": "…" } }`；
  - 数组整份替换（`include`、`exclude`、`weekdays`）；对象写 `null` 回到缺省（`"filter": null` 去掉过滤、`"check": null` 去掉检查命令）；单项回到缺省就写缺省值（各项的缺省见参数说明）。
  返回的 `trigger` 是存下来的样子，超出范围的值会被丢掉，和你写的对一下。
- 只改本机设置：`write_trigger` 给 `node` 和 `local`，不给 `trigger`。
- 排队：`trigger_queue` 的 `queue`：`waive` 把上次执行视为已结束、放行下一个；`clear` 清空排着的；`cancel` 带 `fire` 取消排着的一个。用户要求时才做。

`state` 的取值：off 关着 / waiting 等着到点 / listening 在跑 / restarting 程序退出了等重启 / error 出错（如端口被占用）/ invalid 设置不对 / confirm 命令、工作区或 shell 改过、等确认 / stopped 连续失败被自动停用 / paused 全部暂停中 / elsewhere 另一个 DSH 进程在负责 / unavailable 这里发不了会话。

## 排查

用户说触发器没反应、出错了、被停了，或让你检查一下时：

1. `list`，看 `triggers.cards` 里 `state`、`problem` 不对的卡片；`triggers.paused` 有值是全部暂停着，请用户在工作流中心「触发」页恢复。
2. `read` 那张卡片，带 `include: ["history", "output"]`。
3. 按下表找原因、改好，`test_trigger` 试到对。
4. 自动停用的、停在 `confirm` 的，修好、试过之后用 `local.enabled: true` 重新打开。
5. 告诉用户原因和改了什么。改了脚本内容要说清楚改了哪里：确认的只是命令，脚本内容变了不会再要求确认。

| 看到 | 多半是 | 怎么办 |
|---|---|---|
| 原因里有「找不到命令」 | 没装 Node，或命令、路径写错 | 核对命令；没装 Node 就请用户装 |
| 「启动不了」 | shell 或工作区不对 | 看 `local.shell`、`local.workspace` |
| 「超过 N 秒没结束」 | 检查命令太慢、卡在网络上 | 给网络请求设超时；间隔太短就加长 |
| 「监视程序运行 N 秒后退出了」，或 `restarting` 反复出现 | 脚本报错、依赖没装、连不上、读不到密钥 | 看 `output` 里带 `[err]` 的行，用 `test_trigger` 复现 |
| 「新建不了会话」「发不进去」「还没选……」 | 工作区被删了、选定的会话没了 | 改 `local.workspace` 或请用户重新选会话 |
| `error`，端口被占用 | 别的程序占了端口 | HTTP 的请用户在插件设置里换端口；监视程序自己开的端口改命令参数 |
| `invalid` | 定义不对 | 按 `problem` 改 |
| 「工作流现在执行不了」 | 图有问题，编译不出计划 | `read` 这个工作流看 `problems`，改好图 |
| `confirm` | 命令、工作区或 shell 改过，还没确认 | 核对后给 `local.enabled: true` |
| `elsewhere` / `unavailable` | 另一个 DSH 进程在负责 / 这里发不了会话 | 告诉用户，到负责的那个 DSH 里看 |
| 开着、状态正常，却一直没触发 | 事件行没带 `::trigger::`、关键字太严、去重太长、检查一直返回 1、`change` 第一次只记下 | 看 `history` 里 `skipped` 的原因和 `output` 里最近的行，拿真实样本 `test_trigger` |
| 没出什么事却触发了 | 启动时把已有的东西当新事件打了出来（每次重启都会再触发）；不该触发的行也带了 `::trigger::` | 看 `output` 里带标记的行，改脚本：启动时只记下现状、打日志 |
| 触发得太频繁 | `every` 处理完下一次还返回 0；`change` 比较的内容里带时间戳；关键字太宽 | 改脚本或过滤 |
| `queued` 越积越多，`waiting` 一直是同一个 | 上次执行的运行状态没改成结束 | 看那个实例的状态；确实结束了，经用户同意用 `trigger_queue` 的 `waive` |
| `history` 里有 `declined` | 执行的模型按触发条件判断不需要 | 看它的理由，不对就改触发条件 |
| 触发了，但工作流没做对 | 不是触发器的问题 | 用 `runs`、`state` 看那个实例；背景信息不够就改脚本输出或触发说明 |

## 交付前自检

- [ ] 用 `test_trigger` 试过，`verdict` 和预期一致；定时检查试过满足、不满足两种，监视试过一件、两件挨着的。最后一次改脚本、命令之后又试过。
- [ ] 监视：只有要触发的那一行带 `::trigger::`，启动时不打事件；日志不带标记。
- [ ] `message` 里的背景信息是「背景信息」一节的样子，执行的模型凭它和触发说明就能开工。
- [ ] 关键字放在过滤里、判断放在触发条件里，没写死在脚本里。
- [ ] 密钥、令牌不在脚本、命令、触发说明里。
- [ ] `maxPerHour`、`maxFailures` 没写成 0（用户明说的除外）。
- [ ] 卡片打开了（用户说先别开的除外），`local.state` 正常。
- [ ] 告诉了用户：卡片在哪个工作流、会在什么时候触发、开没开；要跑命令的说清楚跑什么命令、在哪个工作区。
