# 要快：准实时的监视

用户说「一出现就处理」「几秒内」时读这份。

## 先说清能多快

从事件发生到工作流开始做事有三段，跟用户说方案时三段都说：

1. 发现：推送、本机文件一秒内；只能查的，差一个查询间隔。怎么发现按 SKILL.md 的「找示例」挑，能推送的别轮询。
2. 合并：`filter.merge`，监视缺省等 5 秒。
3. 执行：开会话、编译、模型开始干活，一般十几秒起；工作流本身跑多久另算。

例：「文件放进来一秒内发现，模型开始处理还要十几秒，整个工作流跑完约五分钟」。要秒级出结果的直说做不到，能做的是把工作流做短：第一步先做最要紧的那件，慢的放后面或拆成接续的另一个工作流；别放执行前要问用户的问题。

## 设置怎么配

| 用户要 | 这样配 |
|---|---|
| 越快越好 | `filter.merge` 写 0 或 1；轮询的 `every` 调小，但别比对方的限流还短 |
| 一件都不能漏 | `launch.overlap: "queue"`，`queueMax` 按高峰调大；脚本按编号去重（`seenIds`），重启后从游标接着查 |
| 一阵一阵来，一阵处理一次 | `merge` 调到 10 到 60 |
| 只关心最新的，忙时丢掉也行 | `overlap: "skip"`（缺省） |

- `maxPerHour`（缺省 60）在快的场景里容易碰上：按高峰估着调大；用户明说不限才写 0。
- 能在脚本里判断的在脚本里判断，能用关键字筛的放过滤；触发条件每次都占一次模型调用。
- DSH 没开时没人收事件，再启动按游标补上就不漏；但一口气补几百件就是几百次触发，补的时候设上限、超过了只打一件汇总（`examples/records.md` 里有写法）。
