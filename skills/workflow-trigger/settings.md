# 过滤与执行设置

过滤 `filter`（定时检查、监视、HTTP 才有；都不花模型调用；按关键字 → 去重 → 合并的顺序）：

| 字段 | 缺省 | 说明 |
|---|---|---|
| `include` | 无 | 背景信息含其中一个才触发；不分大小写、按原文找子串；最多 20 个 |
| `exclude` | 无 | 含其中任何一个就不触发，优先于 `include` |
| `dedupe` | 0（不去重） | 分钟：一样的内容这么久里只触发一次，最长 7 天 |
| `merge` | 监视、HTTP 5 秒；检查 0 | 秒：从第一段进来算起，这么久里的几次并成一次，最长 3600 |

- 能用关键字筛的放在过滤里，别写死在脚本里：用户在卡片上改得到。
- 关键字按原文找：JSON 里 `"action":"opened"` 和 `"action": "opened"` 不一样。拿真实样本用 `test_trigger` 试过再定。
- 日志一下刷出几十行时调大 `merge`；同一个告警反复来时用 `dedupe`。

执行设置 `launch`：

| 字段 | 缺省 | 说明 |
|---|---|---|
| `session` | `new` | `new` 每次新建会话；`last` 接着上一次的会话（上下文会越来越长）；`fixed` 发进用户选定的会话（`local.session`，`"current"` 是当前会话） |
| `overlap` | `skip` | 上一次触发的执行还没结束时：`skip` 跳过；`queue` 排队，结束一个再发下一个；`parallel` 同时运行 |
| `queueMax` | 10 | 排队时最多排几个，排满了再来的跳过；0 = 不限 |
| `catchUp` | true | 定时：DSH 没开时错过的，启动后补一次 |
| `maxPerHour` | 60 | 每小时最多触发几次，超过的跳过（排队的也算）；0 = 不限，用户明说才这样写 |
| `maxFailures` | 3 | 连续失败几次自动停用；0 = 不停用，用户明说才这样写 |

- 「执行结束」看那次执行的运行状态：整体状态改成 `done` / `failed` / `cancelled` 才算；还没开始执行、等回复都算没结束。所以 `skip`、`queue` 要工作流开着「记录运行状态」，没开时卡片打不开。
- 会改工作区文件的工作流（切分支、改代码、跑构建）用 `queue`；只读、只回消息、只写总结的可以 `parallel`。
- 「失败」只算触发器自己干不了活（命令跑不起来、监视程序一启动就退出、会话建不出来）；条件不满足、过滤掉、跳过、工作流执行失败都不算。
